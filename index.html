02 Experiment · Section 9

One person, agents,
one loop.

The question: what does it take to run AI agents like a small engineering team, and keep it safe, useful and cheap?

  1. 01

    Task

    the board

    An issue with a definition of done, an agent label and a label for who it waits on.

  2. 02

    Pull

    the dispatcher

    One task at a time, and none while review is full. Review is the scarce resource.

  3. 03

    Build

    an agent

    On a branch, in a sandbox that holds no model keys. It opens a pull request and stops.

  4. 04

    QA

    a second agent

    Builds it and uses it on desktop and phone. The verdict never comes from the author.

  5. 05

    Review

    the coordinator

    Green CI, a QA pass and a read of the diff, then the merge. The agents never merge.

  6. 06

    Measure

    the ledger

    Every run is logged: agent, model, duration, outcome and cost.

The crew

agents on low-cost models, each with one job, a monthly budget and a time limit per run. A coordinator writes their tasks and reviews their work; I set the rules and read the reports.

What gets measured

A team of agents is managed like any other team: by what it costs, what it finishes and what comes back from review.

  • Budget

    A hard monthly cap, a ceiling per agent and a cap on runs per day. Every run is booked to an owner; spend nobody owns is treated as a bug.

  • Models

    An agent can be moved to another model from an allow-list, one run at a time. The ledger records the model asked for and the model that answered, so trials are compared on cost and outcome.

  • Timeouts

    A run that hits its time limit delivers nothing, so the rate is tracked per agent. The coder's was about 40% in the first week it was measured; the target is under 15%, and the lever is smaller tasks.

  • Code health

    Hypothesis: healthier code makes an agent's next change cheaper and more reliable. Every repository is being brought to a CodeScene Code Health of 9.5 or more. Being measured; no result yet.

03 Experiment · live

Flight Tracker

The experiment that got the most thought: live aircraft worldwide, with their position history. The question: how far does a deliberately simple architecture go on a real-time problem?

Open the live app ↗

What the experiment tests

  • One process

    REST, WebSocket and the pollers share one JVM. Live state is a map in memory, not a table.

  • One file

    SQLite with an append-only position history, kept for 72 hours. Distance and airborne hours are derived from it.

  • One map

    A single MapLibre GL map: basemap, airports, trails and planes are all GL layers. No framework.

  • Deploy on merge

    The deploy waits for the health endpoint to report the exact commit it shipped, and rolls back if it never does.

  • Built with agents

    Agents open pull requests here too. None merges without a QA pass, a review and green CI.
